Retos

Devin Desktop Workshop · Mexico Tech Week · workshop-devin

Un administrador de torneos (single elimination y Swiss, hasta 32 jugadores) con un motor de reglas puro y una app React que guarda todo en el navegador. Aquí las decisiones no son de código sino de reglas de torneo: en cuántas cosas Devin va a necesitar que tú, el organizador, decidas. Hay cinco retos; no tienes que hacerlos todos.

Cómo trabajar cada reto

Entiende (dale contexto con @-menciones), planea (Plan mode), actúa (Implement) y verifica (tests, Quick Review, Merge).

Antes de empezar

Necesitas Node y npm. Es un monorepo con dos workspaces: el motor de reglas (packages/tournament-engine, TypeScript puro, sin React) y la app del organizador (apps/master-web, React + Vite + Zustand + Dexie).

npm install
npm test            # pruebas del motor (Vitest)
npm run build       # build de la app web
npm run dev         # abre http://localhost:5173

Los datos viven en IndexedDB del navegador. Para empezar de cero: DevTools → Application → IndexedDB → borra la base tournament-runner.

Reglas

  1. Empieza cada reto en Plan mode. Lee el plan, corrígelo y solo entonces aprieta Implement.
  2. Las reglas de torneo las decides tú. Si Devin dice "asumí que…", párale y decide tú.
  3. Primero la prueba que falla, luego el arreglo. Que Devin te enseñe el test en rojo antes de implementar.
  4. Una sesión por reto. Para el reto Paralelo usa Worktree y revisa con Quick Review antes del Merge.
  5. No le pidas a Devin que edite README.md: el archivo está codificado en UTF-16 y se puede corromper.

Ojo con esto

  • npm run typecheck puede fallar en el motor con errores de node:fs, node:path o __dirname (falta @types/node). Es un problema conocido de la línea base. Para revisar tipos de la app usa npm run typecheck --workspace @tourney/master-web.
  • npm test reescribe los archivos de sample-data/ con ids y fechas nuevas, y npm run build modifica apps/master-web/dist/. Antes de revisar un diff o de hacer commit, limpia con git checkout -- sample-data apps/master-web/dist.
  • Un Worktree nuevo **no trae node_modules**. Corre npm install dentro del Worktree antes de probar.
  • El documento IMPLEMENTATION.md dice que la app no necesita lógica por formato y que el bracket "nunca se atora". Ambas cosas son más optimistas que el código. Confía en el código y en los tests.

Retos

Ruta sugerida (~60 min): 1, y luego 2 o 3. Si vas rápido, 4. El 5 es el más grande: el motor primero, la interfaz después.

  1. Importar CSV (Core, 15–20 min)
  2. El bracket que se atora (Core, 15–20 min)
  3. Win% de 200 (Core, 15–20 min)
  4. Round Robin y selector (Paralelo, 20–25 min)
  5. Modo media (Jefe, 25–35 min)

Reto 1 · Importar jugadores desde un .csv

Core · 15–20 min · Plan mode, Parser puro, Tests, UI

Del archivo de Excel del organizador a un torneo listo. Las fotos de perfil llegan en otra fase.

La misión

En la pantalla de Setup, un botón Importar CSV que deje elegir un archivo, muestre una vista previa con los jugadores válidos y los errores por fila (con número de línea y mensaje claro), y solo al confirmar agregue los jugadores al torneo.

Piensa en los CSV reales que salen de Excel en México: separador ;, comillas, acentos, con o sin encabezado, líneas vacías. Para las fotos, solo deja el hook mínimo en el modelo; no construyas la interfaz de fotos todavía.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Quiero importar jugadores desde un .csv en la pantalla de Setup (@apps/master-web/src/views/SetupView.tsx), con vista previa y errores por fila. Plan mode primero.

Lo que tú decides

  • ¿Dónde vive el parser? El motor no tiene DOM, así que recibe un string, no un File.
  • Si una fila falla: ¿importas todo o nada, o solo las filas válidas? ¿Agregas a los existentes o reemplazas la lista?
  • Nombres repetidos: ¿bloquear, advertir o desambiguar?
  • Si el CSV trae una columna seed, ¿se respeta siempre o solo en modo de siembra manual? ¿Y se lo dices al usuario en la vista previa?
  • Más de 32 jugadores: ¿rechazas el archivo o truncas con aviso? ¿Cuentas a los que ya estaban?
  • Para fotos: ¿una imagen embebida en el jugador o guardada aparte? ¿Subes schemaVersion?

¿Cómo sabes que terminó?

  • npm test
  • npm run build
  • npm run typecheck --workspace @tourney/master-web

Archivos que vas a ver

packages/tournament-engine/src/import/csv.ts (nuevo) packages/tournament-engine/src/operations.ts packages/tournament-engine/src/model/types.ts packages/tournament-engine/src/serialization.ts packages/tournament-engine/tests/ (tests nuevos) apps/master-web/src/views/SetupView.tsx apps/master-web/src/components/ (modal de importación)

Si te atoras

Pista 1
El motor no tiene DOM. Piensa qué función pura puede recibir un string y devolver las filas válidas más una lista de errores por línea. La interfaz solo lee el archivo y muestra ese resultado.
Pista 2
Importar fila por fila con addPlayer puede dejar el torneo a medias si una falla. Considera una operación única que valide todo (borrador, tope de 32 contando los que ya estaban, nombres vacíos, seeds repetidos) y solo entonces agregue a todos.
Pista 3
Para el CSV de Excel: quita el BOM, soporta CRLF y comillas escapadas, detecta el separador contando , ; y tabulador en la primera línea fuera de comillas, y reconoce encabezados por alias sin acentos. Lee el archivo como ArrayBuffer y decodifica con TextDecoder.
Trampas conocidas (al final)
  • Excel en español guarda a veces en Windows-1252 y no en UTF-8: file.text() da mojibake (Jos�). Lee el ArrayBuffer, intenta UTF-8 estricto y cae a windows-1252.
  • El BOM U+FEFF hace que el primer encabezado Nombre no coincida con nada. Quítalo.
  • Un encabezado que no reconoces (por ejemplo Participante) se interpreta como fila de datos y crea un jugador llamado "Participante". Decide y pruébalo.
  • Las columnas seed solo tienen efecto en modo manual: los otros modos las sobrescriben, y las flechas ↑↓ del Setup renumeran todo. Sin aviso, el usuario cree que se respetaron.
  • updatePlayer no exige que el torneo esté en borrador. La protección "no importar con el torneo iniciado" debe ir explícita en la operación nueva.

Reto 2 · El bracket que se atora

Core · 15–20 min · Plan mode, Bug real, Prueba primero

La documentación dice "nunca se atora". Descalifica al seed 1 en un torneo de tres y compruébalo.

La misión

Hay un bug real en la eliminación simple. Con 3 jugadores, si descalificas al seed 1 (que tenía el bye) y juegas P2 vs P3, el torneo se queda activo sin campeón. Pasa también al dar de baja a un jugador que ya avanzó, o con un empate en una semifinal.

Hay dos problemas con el mismo síntoma: una causa raíz en el código, y una regla de negocio sin definir (¿qué hace un empate en eliminación directa?). Primero la prueba que falla.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Con 3 jugadores, si descalifico al seed 1 el torneo se queda activo sin campeón. Escribe primero una prueba que falle en @packages/tournament-engine/tests/single-elimination.test.ts y explícame la causa en Plan mode.

Lo que tú decides

  • Para un empate (o doble derrota) en eliminación directa: ¿rechazarlo, pedir repetición del partido, o desempatar por seed?
  • ¿El arreglo es normalizar dónde cae el jugador del bye, o cambiar cómo se calcula el ganador?
  • Si ya no se permiten ciertos resultados, ¿la interfaz deja de ofrecer esos botones?

¿Cómo sabes que terminó?

Trampas conocidas (al final)

  • La documentación dice "nunca se atora" y el código lo desmiente. Después de arreglar, corrige IMPLEMENTATION.md.

Reto 3 · Win% de 200%: arregla los byes en los standings

Core · 15–20 min · Plan mode, Bug real, Reglas de desempate

Un porcentaje de victorias no puede pasar de 100%. En un Swiss de 5 jugadores, sí pasa.

La misión

Reproducción: un Swiss de 5 jugadores, donde gana siempre el jugador A durante 2 rondas. P5 (1 bye y 1 victoria) muestra Win% 200% y P3 (0-2) muestra Opp% 150%.

Hay varias convenciones válidas en torneos reales para tratar los byes. Elegir una es decisión tuya; ningún porcentaje puede salir de 0–100%.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

En un Swiss de 5 jugadores, un jugador con bye muestra Win% 200%. Escribe primero la prueba que falla (@packages/tournament-engine/tests/standings.test.ts) y dame opciones de convención antes de implementar.

Lo que tú decides

  • ¿El bye cuenta como un partido ganado (100%), no cuenta para Win% (convención de Magic: solo suma puntos), o simplemente se recorta a 100%?
  • ¿Hay un piso para el porcentaje de un rival al calcular Opp% (por ejemplo, 33%)?
  • ¿Qué tests existentes sobre el bye cambian? ¿Con qué justificación?

¿Cómo sabes que terminó?

  • npm test

Archivos que vas a ver

packages/tournament-engine/src/standings/index.ts packages/tournament-engine/tests/standings.test.ts apps/master-web/src/views/StandingsView.tsx IMPLEMENTATION.md

Si te atoras

Pista 1
Mira matchWinPct y qué entra al numerador y al denominador cuando hay un bye.
Pista 2
Cambiar el Win% de un jugador cambia el Opp% de sus rivales: revisa los dos juntos.
Trampas conocidas (al final)
  • Devin suele elegir "recortar a 1.0" (un parche) o la convención de Magic sin avisar. Exige las opciones con sus costos antes de decidir.
  • La documentación dice "convención de Magic" pero no implementa el piso del 33%.
  • Comparar porcentajes con === falla por redondeo de floats: dos jugadores matemáticamente empatados no empatan.

Reto 4 · Dos frentes: motor de Round Robin y selector de torneos

Paralelo · 20–25 min · Worktree, Paralelo, Quick Review, Merge

Un formato nuevo en el motor y una lista de torneos en la app. Dos zonas del repo, dos agentes, un Merge.

La misión

Sesión A: un nuevo formato, Round Robin (todos contra todos), como un TournamentFormatEngine más. Sesión B: un selector de torneos: hoy la app solo carga el torneo más reciente y los anteriores se quedan olvidados en IndexedDB.

Cada una en su propia sesión Worktree. Cuando terminen, Quick Review de cada diff y luego Merge. Después, el paso de 3 minutos: exponer Round Robin en SetupView. Ese archivo no lo toca ninguna de las dos sesiones.

Reto 5 · Jefe: modo media, la pantalla del proyector

Jefe · 25–35 min · Megaplan, Sincronización, Sin servidor

Una pantalla adicional que muestra standings, pareos y resultados conforme el organizador los captura.

La misión

Una vista de solo lectura que se abre en otra ventana (un proyector, un segundo monitor) y se actualiza sola mientras el organizador captura resultados en el panel. Todo 100% offline, en el mismo navegador, sin servidor.

Tiene que leerse a distancia (letra grande), rotar sola entre standings, ronda actual y bracket, y no mostrar datos sensibles del arbitraje: notas, razones de warnings o penalizaciones, razones de drop y descalificación, historial.

Una ayudita para arrancar

Es solo el comienzo. Escribe tu propio prompt y complétalo con lo que pide la misión.

Quiero un modo media: una segunda ventana de solo lectura que muestre standings y pareos en vivo, sin servidor. Pide un megaplan y propón cómo se sincronizan las ventanas antes de escribir código.

Lo que tú decides

  • ¿Quién es la fuente de verdad? ¿El panel publica y la ventana media es una réplica, o la ventana media lee IndexedDB?
  • ¿Qué se transmite: el torneo completo ya limpiado o parches? Con 32 jugadores, ¿cuál es más simple y menos propenso a desincronizarse?
  • ¿Qué ve la ventana media si se abre después que el panel? ¿Y si el panel está cerrado?
  • ¿Qué datos se ocultan? ¿Los nombres de jugadores descalificados? ¿El conteo de warnings?
  • Swiss no tiene bracket: ¿qué escenas rotan en cada formato y cada cuántos segundos?

¿Cómo sabes que terminó?

  • npm run build
  • npm run typecheck --workspace @tourney/master-web

Archivos que vas a ver

apps/master-web/src/media/ (nuevo) apps/master-web/src/main.tsx apps/master-web/src/App.tsx apps/master-web/tests/ (nuevo)

Si te atoras

Pista 1
Piensa en una sola fuente de verdad: el panel ya tiene el estado en Zustand. La ventana media solo debería recibir copias y nunca importar el store ni la capa de Dexie. ¿Qué API del navegador permite hablar entre pestañas del mismo origen sin servidor?
Pista 2
Usa BroadcastChannel con un mensaje que la ventana media envía al abrirse (para pedir el estado actual) y que el panel responda; además el panel publica cada vez que cambia el torneo. Antes de emitir, pasa el torneo por una función que quite los datos sensibles.
Pista 3
Estructura: un módulo puro de canal con interfaz mínima para probarlo con Vitest, un número de secuencia por emisor para ignorar mensajes viejos, y en main.tsx decide por ?view=media qué raíz renderizar.
Trampas conocidas (al final)
  • StrictMode de React monta los efectos dos veces: crea y cierra el BroadcastChannel dentro de un useEffect con limpieza, y haz idempotente al publicador.
  • La app web no tiene Vitest propio: funciona porque el del motor está elevado. Para un npm test limpio, agrégalo como dependencia de desarrollo.
  • El tsconfig de la app solo incluye src: los tests nuevos no se tipan, y node:fs o __dirname en tests falla por falta de @types/node.
  • El typecheck de la raíz ya falla en la línea base por el motor: corre el de @tourney/master-web por separado.
  • addPlayer(t, displayName) recibe un string, no un objeto; es un error fácil al escribir tests.
  • Que la vista media sea de solo lectura se logra con la estructura de imports, no con el navegador. Pruébalo.
